# Публикация и разбор потерь

## Перед первой командой

1. `indexgap init` в корне проекта пишет `indexgap.json`; дальше команды идут без путей и флагов.
2. Покажи человеку, что `init` угадал: каталог страниц, адрес сайта, профиль, датасет. Попроси подтвердить.
3. Каталог страниц — тот, что на сайте отдаётся как `/`; от него считаются адреса в sitemap и IndexNow.
4. Ключ IndexNow свой у каждого домена: `indexgap init --key` выдаёт новый, чужой даёт 403.
5. Нет команды `indexgap`: `pipx install indexgap`; из исходников — `pipx install -e <путь>` или `PYTHONPATH=<путь> python3 -m indexgap`.

## Порядок

1. `indexgap check --strict` проходит — или человек принял каждую оставшуюся critical-находку.
2. Сборка, затем `indexgap sitemap`: генератор мог стереть `sitemap.xml` вместе с каталогом.
   Есть копия того, что на проде, — `indexgap diff ./prod-build ./out --strict`: пропавшие
   и закрывшиеся страницы, правки шаблона. Critical там — показать человеку до деплоя.
3. Деплой. Убедись, что живы `https://сайт/<ключ>.txt` и одна изменённая страница.
4. `indexgap notify` пробным прогоном → показать человеку → `--send` после явного согласия.

`notify` отмечает адреса отправленными по хешу локального текста. Отправка
до деплоя — поисковик обойдёт старую версию, а изменение больше не уйдёт.
Очередь собирается и при открытых critical: `notify` только предупреждает,
если в `indexgap-check.json` текущего каталога они есть у отправляемых страниц.

## Sitemap

```bash
indexgap sitemap ./out --site https://example.com --out-dir ./out
```

Шардинг после 45 000 URL делается сам. `lastmod` меняется только когда изменился
текст: если он равен дате сборки у всех страниц сразу, поисковик перестаёт
ему верить. Хеш считается по основному тексту, заголовку и описанию — правка
пункта меню не помечает изменённым весь сайт.

Если `--out-dir` не корень публикации, а подпапка, добавь `--public-prefix`
с путём, по которому файлы будут доступны на сайте: иначе индекс шардов
сошлётся на корень, а файлы будут лежать в другом месте.

Черновики (`status: draft` во фронтматтере) в sitemap не попадают — команда
пишет, сколько их. Чужие `sitemap-news.xml` и `sitemap-images.xml` в каталоге
публикации пакет не трогает.

**Манифест.** Состояние — lastmod, очередь отправки, список созданных файлов
sitemap — живёт в `.indexgap-manifest.json` рядом с `indexgap.json`; без
`indexgap.json` — рядом со страницами, поэтому сначала `init` (или `--manifest`).
**Его коммитят**: без него каждая сборка в CI считает все страницы новыми.
В публикуемый каталог он попадать не должен: старый манифест, лежащий рядом
со страницами, подхватывается и дальше — перенеси его к `indexgap.json`.

## IndexNow

```bash
indexgap notify ./out --site https://example.com --key <свой-ключ>
```

Ключ: 8–128 символов латиницы, цифр и дефиса (подойдёт uuid без скобок).
Он же становится файлом `<ключ>.txt` в **корне сайта**:

```bash
indexgap notify ./out --site https://example.com --key <свой-ключ> \
    --write-key --key-dir ./out
```

`--key-dir` — каталог публикации, не каталог с исходниками: файл ключа рядом
с markdown на сайт не попадёт, и протокол ответит 403. Если файл лежит не в
корне, его адрес задаёт `--key-location`.

**Если сборка стирает каталог публикации**, всё, что положено туда руками,
пропадёт при следующей сборке. Файл ключа держи в статических файлах генератора
(`static/`, `public/` — то, что копируется в сборку каждый раз), а `indexgap
sitemap` запускай после каждой сборки.

По умолчанию — пробный прогон: в IndexNow ничего не уходит, команда печатает,
сколько адресов новых, изменённых, без изменений и исчезнувших, и первые
20 адресов очереди. Отправка —
флагом `--send` после явного согласия. Уходит только изменившееся: каждый URL
расходует краул-квоту сайта. Исчезнувшую страницу, если она была опубликована,
закрой 301-м редиректом на ближайшую живую.

Без манифеста `--send` откажется: он отправил бы весь сайт. Если это
действительно первая отправка — добавь `--first`. Если манифест потерян
(чистая сборка в CI) — верни его, а не отправляй сайт целиком на каждом деплое.

Если часть батчей не принята, принятые всё равно отмечаются и повторно
не поедут; остальные останутся в очереди.

Пробный прогон в сеть не ходит. С `--send` скачивается реестр участников
протокола; `--offline` обходится без него — возьмётся кэш или встроенный
список. Кэш лежит в домашнем каталоге пользователя, не рядом со страницами.

**Обязательно проговори, кого IndexNow НЕ покрывает.** Команда печатает состав
участников (bing, yandex, seznam, naver, yep и другие) и отдельно — кого там
нет. Google в протоколе не участвует: для него остаются sitemap, строка
`Sitemap:` в robots.txt и Search Console. Человек, который этого не знает,
будет ждать от отправки эффекта в Google и не дождётся.

robots.txt тоже должен лежать в корне публикации; если этот каталог
собирается, его выпускает генератор.

## Когда трафика нет

```bash
indexgap doctor ./out --site https://example.com \
    --sitemap ./out/sitemap.xml \
    --indexed gsc.csv --indexed bing.csv --indexed yandex.csv
```

Строит воронку и объясняет каждую потерю адресно. Страница может попасть
сразу в несколько причин — обе правки нужны. В причину «почти-дубли» идут
только пары выше порога дубля: между `similar` canonical не ставят. Отчёт —
`indexgap-doctor.html`; контентные проверки здесь не запускаются, их делает
`indexgap check`.

### Про выгрузки

В Search Console два разных «Страницы»:

* **Индексирование → Страницы** → «Просмотреть данные о проиндексированных
  страницах» → Экспорт — настоящий список индекса (до 1000 строк). Проси его.
* **Эффективность → Страницы** → Экспорт — отчёт о показах. Страница в индексе
  без показов в него не попадёт: отсутствие здесь ≠ «не в индексе». На новом
  сайте это систематически завышает потери — скажи об этом человеку.

Формат панелей разный; кодировка и разделитель определяются сами, cp1251
и точка с запятой читаются. Если пакет не уверен, чей это экспорт, он попросит
метку: `--indexed yandex=export.csv`. Две выгрузки под одной меткой сливаются
в один индекс, и сравнение поисковиков исчезает.

### Если панели вебмастера нет

Читаются Ahrefs, Semrush, Screaming Frog, Sitebulb, GA4, Matomo или просто
список адресов: CSV с любым разделителем и кодировкой, XLSX, JSON, NDJSON,
XML-карта, адрес по строке.

```bash
indexgap doctor ./out --site https://example.com \
    --indexed ahrefs=top-pages.xlsx --indexed ga4=pages.csv
```

**Это разные утверждения, и путать их нельзя.** Панель вебмастера отвечает
«знает ли поисковик про страницу» прямо. Аналитика доказывает индекс только
для страниц, куда кто-то зашёл, — её молчание ничего не значит. Краулер
доказывает обход, а не индексацию. Ahrefs и Semrush — их собственный индекс,
а не индекс Google. Пакет держит это разделение сам: подпись шага воронки
меняется вместе с источником. Есть Search Console — проси её, остальное
дополняет; нет — работай с тем, что есть, но не называй результат индексацией.

**Проси выгрузки из всех панелей, где сайт подтверждён, а не только из Google.**
Когда выгрузки — списки индекса, это меняет диагноз:

* страницы нет **нигде** — техническая проблема, чинится по разделу «почему
  страницы не в индексе»;
* страницы нет **только в одном** поисковике — остальные её приняли, значит
  она доступна и валидна. Дело в оценке качества или скорости индексации
  этим поисковиком, и техническими правками это обычно не лечится.

С выгрузками показов (Эффективность, аналитика) этот вывод не делается:
отсутствие там значит «ещё не было показов». Bing и Яндекс обычно индексируют
быстрее Google — расхождение в первые недели часто означает «ещё не дошли».

Категорию «причина не установлена локально» назови честно: часто прошло
просто мало времени с публикации. И покажи, где смотреть самому — Search
Console и Вебмастер. Если отчёт говорит одно, а Search Console другое, прав
Search Console.
