# Публикация и разбор потерь

## Sitemap

```bash
indexgap sitemap ./content --site https://example.com --out-dir ./public
```

Шардинг после 45 000 URL делается сам. `lastmod` меняется только когда изменился
текст: если он равен дате сборки у всех страниц сразу, поисковик перестаёт
ему верить. Хеш считается по основному тексту, заголовку и описанию — правка
пункта меню не помечает изменённым весь сайт.

Если `--out-dir` не корень публикации, а подпапка, добавь `--public-prefix`
с путём, по которому файлы будут доступны на сайте: иначе индекс шардов
сошлётся на корень, а файлы будут лежать в другом месте.

Черновики (`status: draft` во фронтматтере) в sitemap не попадают — команда
пишет, сколько их. Это не повод не запускать `check` перед публикацией,
но одну типовую ошибку закрывает.

Состояние живёт в `.indexgap-manifest.json` рядом со страницами: lastmod, очередь
отправки и список файлов sitemap, созданных пакетом. Внеси его в `.gitignore`
статического генератора, чтобы он не уехал в сборку. Чужие `sitemap-news.xml`
и `sitemap-images.xml` в каталоге публикации пакет не трогает.

## IndexNow

```bash
indexgap notify ./content --site https://example.com --key <свой-ключ>
```

Ключ человек придумывает сам: 8–128 символов латиницы, цифр и дефиса
(подойдёт uuid без скобок). Он же становится именем файла в **корне сайта**:

```bash
indexgap notify ./content --site https://example.com --key <свой-ключ> \
    --write-key --key-dir ./public
```

`--key-dir` — это каталог публикации, не каталог с исходниками. Файл ключа,
положенный рядом с markdown, на сайт не попадёт, и протокол ответит 403.

По умолчанию пробный прогон. Покажи человеку, сколько и каких URL уйдёт,
и отправляй только после явного согласия — флагом `--send`. Отправляется
только изменившееся: каждый URL расходует краул-квоту сайта.

Если часть батчей не принята, принятые всё равно отмечаются и повторно
не поедут; остальные останутся в очереди.

**Обязательно проговори, кого IndexNow НЕ покрывает.** Команда печатает состав
участников из реестра протокола (bing, yandex, seznam, naver, yep и другие)
и отдельно — кого там нет. Google в протоколе не участвует: для него остаются
sitemap и Search Console. Человек, который этого не знает, будет ждать
от отправки эффекта в Google и не дождётся.

В CI без сети — флаг `--offline`, возьмётся кэш или встроенный список.
Кэш реестра лежит в домашнем каталоге пользователя, не рядом со страницами.

## Когда трафика нет

Главная команда пакета:

```bash
indexgap doctor ./content --site https://example.com \
    --sitemap ./public/sitemap.xml \
    --indexed gsc.csv --indexed bing.csv --indexed yandex.csv
```

Строит воронку и объясняет каждую потерю адресно. Страница может попасть
сразу в несколько причин — так и бывает, и обе правки нужны.

В причину «почти-дубли» попадают только пары выше порога дубля. Страницы,
помеченные как `similar`, туда не идут: ставить между ними canonical нельзя.

Отчёт пишется в `indexgap-doctor.html`. Контентные проверки здесь не запускаются —
их делает `indexgap check`.

### Про выгрузки

Экспорт «Страницы» из Search Console — это **отчёт о показах**, а не об
индексации: страница в индексе без показов в него не попадёт. На новом сайте
это систематически завышает потери, и человеку об этом надо сказать, иначе
он побежит чинить то, что работает.

Формат панелей разный; кодировка и разделитель определяются сами, cp1251
и точка с запятой читаются. Если пакет не сможет уверенно определить, чей это
экспорт, он скажет об этом и попросит метку: `--indexed yandex=export.csv`.
Не оставляй это на самотёк: две выгрузки под одной меткой сливаются в один
индекс, и сравнение поисковиков исчезает.

### Если панели вебмастера нет

Search Console есть не у всех, а Ahrefs, Semrush, Screaming Frog, Sitebulb,
GA4, Matomo или просто список адресов — почти у каждого. Всё это читается:
CSV с любым разделителем и кодировкой, XLSX без пересохранения, JSON, NDJSON,
XML-карта, список адресов по строке.

```bash
indexgap doctor ./content --site https://example.com \
    --indexed ahrefs=top-pages.xlsx \
    --indexed screamingfrog=internal_html.csv \
    --indexed ga4=pages.csv
```

**Но это разные утверждения, и путать их нельзя.** Панель вебмастера отвечает
на вопрос «знает ли поисковик про страницу» прямо. Аналитика доказывает, что
страница в индексе, но только для тех страниц, куда кто-то зашёл, — молчание
аналитики ничего не значит. Краулер доказывает обход, а не индексацию. Ahrefs
и Semrush — это их собственный индекс, а не индекс Google.

Пакет держит это разделение сам: подпись шага воронки меняется вместе
с источником, а если рядом с панелью стоит краулер, он прямо говорит, что
цифра шага выше реальной индексации. Сравнение «есть у одного, нет у другого»
делается только между панелями.

Что говорить человеку: если у него есть Search Console — проси её, остальное
дополняет. Если нет — работай с тем, что есть, но не называй результат
индексацией.

**Проси выгрузки из всех панелей, где сайт подтверждён, а не только из Google.**
Это меняет диагноз, а не уточняет его:

* страницы нет **нигде** — техническая проблема, чинится по разделу «почему
  страницы не в индексе»;
* страницы нет **только в одном** поисковике — остальные её обошли и приняли,
  значит она доступна и валидна. Дело в оценке качества этим поисковиком либо
  в скорости индексации, и техническими правками это обычно не лечится.

Без разбивки обе ситуации выглядят одинаково, и человек чинит не то.
Bing и Яндекс обычно индексируют быстрее Google — расхождение в первые недели
часто означает просто «ещё не дошли», а не проблему.

Категорию «причина не установлена локально» назови честно: часто дело просто
в том, что прошло мало времени с публикации.

И покажи, где смотреть результат самому — Search Console и Вебмастер.
Если отчёт говорит одно, а Search Console другое, прав Search Console.
